# Hexalyte SaaS Integration Adapter Contract & Specification

This document defines the interface and protocol contract for integrating external SaaS applications with the Hexalyte Central Reseller Platform.

---

## 1. Architecture Overview

The Hexalyte Central Reseller Platform acts as a commercial distribution hub. It **does not store SaaS operational data** (products, inventory, sales, customer records). It only manages:
- Reseller accounts, tiers, and commissions.
- Client business references (`Customer`).
- Product subscription mapping (`CustomerAccount`).
- Verified payment records and bank slips (`ActivationRequest`).

All external SaaS communication is strictly encapsulated behind the `SaasIntegration` interface in [`saas-integration.ts`](file:///d:/reseller/Hexalyte-Reseller/apps/backend/src/modules/integrations/saas-integration.ts).

```
[ Reseller UI / API ]
         │
         ▼
[ Central Platform Core ]
 (Commissions, Tiers, Bank Slips)
         │
         ▼
[ Integration Layer (SaasIntegration) ]
         ├── ManualIntegration (Pre-Integration / Awaiting API)
         ├── MobileShopIntegration
         ├── FashionErpIntegration
         ├── SalonIntegration
         └── SupermarketIntegration
```

## 2. Standard Partner API Interface (`SaasIntegration`)

Every external SaaS provider adapter implements this contract:

```typescript
export interface SaasIntegration {
  readonly provider: string
  readonly supportsRemoteQueries: boolean
  lastHttpStatus?: number

  /** Provisions a new tenant trial account in the external SaaS. */
  createTrial(input: CreateTrialInput): Promise<CreateTrialResult>

  /** Finds an existing tenant by reference in the external SaaS. */
  findTenantByReference(externalRef: string): Promise<AccountStatus | null>

  /** Fetches current tenant subscription status from the external SaaS. */
  getAccountStatus(externalTenantId: string): Promise<AccountStatus | null>

  /** Requests immediate paid subscription activation for a tenant. */
  activateSubscription(input: ActivateSubscriptionInput): Promise<ActivationResult>

  /** Checks status of a previously queued activation request. */
  getActivationStatus(requestId: string): Promise<ActivationResult | null>

  /** Verifies API connectivity and credentials. */
  healthCheck(): Promise<HealthResult>
}
```

## 3. Security & Authentication Protocol

When an external SaaS product provides its partner API, outbound calls from the Central Platform use:

1. **Bearer Token Authentication**:
   - `Authorization: Bearer <API_KEY>`
2. **HMAC-SHA256 Signature Verification**:
   - Outbound requests are signed using the configured `signingSecret` over `timestamp + "." + body`.
   - Headers:
     - `X-Hexalyte-Timestamp`: Current UTC ISO timestamp (e.g., `2026-10-12T04:00:00.000Z`).
     - `X-Hexalyte-Signature`: Hex-encoded HMAC-SHA256 digest.
3. **Idempotency**:
   - `Idempotency-Key`: UUID generated by the Central Platform. Retries reuse the same key to prevent duplicate provisioning or double billing.

## 4. Provider-Specific Adapter Contracts

### A. Hexalyte Mobile Shop (`MOBILE_SHOP`)
- **Category**: Mobile phone shop POS & inventory management SaaS.
- **Provider Key**: `MOBILE_SHOP`
- **Adapter Class**: `MobileShopIntegration` extends `PartnerApiIntegration`
- **Payload Mapping**:
  - `shopName`: maps to `businessName`
  - `ownerName`: maps to `contactName`
  - `ownerEmail`: maps to `contactEmail`
  - `phone`: maps to `contactPhone`
  - `tenantId`: normalized to `externalTenantId`
  - `ownerUserId`: normalized to `externalAccountId`

### B. HexaOne Clothing ERP (`FASHION_ERP`)
- **Category**: Garment and fashion retail multi-branch ERP SaaS.
- **Provider Key**: `FASHION_ERP`
- **Adapter Class**: `FashionErpIntegration` extends `PartnerApiIntegration`
- **Payload Mapping**:
  - `companyName`: maps to `businessName`
  - `adminContact`: `{ name, email, phone }`
  - `tenantId`: normalized to `externalTenantId`

### C. Hexalyte Salon (`SALON`)
- **Category**: Salon and spa appointment management SaaS.
- **Provider Key**: `SALON`
- **Adapter Class**: `SalonIntegration` extends `PartnerApiIntegration`
- **Payload Mapping**:
  - `name`: maps to `businessName`
  - `owner_name`: maps to `contactName`
  - `owner_email`: maps to `contactEmail`
  - `owner_phone`: maps to `contactPhone`
  - `plan`: `'trial'` (for trials) or snake_case subscription attributes

### D. Hexalyte Supermarket POS (`SUPERMARKET`)
- **Category**: Supermarket and grocery retail POS SaaS.
- **Provider Key**: `SUPERMARKET`
- **Adapter Class**: `SupermarketIntegration` extends `PartnerApiIntegration`
- **Status**: Pre-launch (`COMING_SOON`), manual fulfilment only.

## 5. Pre-Integration / Manual Fulfilment Workflow

During the pre-integration stage (before external SaaS APIs are live or configured):

1. **Free Trials**:
   - Resellers submit trial requests normally through the platform.
   - The platform creates the `TrialRequest` record in `SUBMITTED` status.
   - The corresponding `CustomerAccount` is stored in `PENDING` status.
   - The trial is **never** marked `PROVISIONED` without an actual `externalTenantId`.
   - Administrators view pending trial requests and manually set up accounts in the SaaS console, then link the tenant ID.

2. **Paid Activations**:
   - Resellers upload payment bank slips and transfer details normally.
   - Requests enter `PENDING_REVIEW`.
   - Administrators match the bank slip against company bank records and start review (`UNDER_REVIEW`).
   - Payment is verified (`PAYMENT_VERIFIED`).
   - Administrative approval moves the request to `APPROVED` ("Approved – awaiting external SaaS activation").
   - **Internal approval is strictly decoupled from SaaS activation**:
     - The customer account remains in `TRIAL` or `PENDING` (not `ACTIVE`).
     - No commission is applied until the external subscription is confirmed.
     - When external activation is completed in the SaaS console, the administrator enters the confirmed external reference via `POST /activation-requests/:id/complete` with `activationReference` and `externalTenantId`.
     - Only upon explicit completion does the customer account transition to `ACTIVE` and generate a `Commission` entry.

## 6. Product Integration Readiness States

Admins monitor integration readiness via `toSafeConfig`:

| Readiness State | Meaning |
|---|---|
| `MANUAL_FULFILMENT` | Pre-integration stage. Provider API not connected; requests are queued for manual administrative fulfilment. |
| `AWAITING_CREDENTIALS` | Remote provider selected, but Base URL, API Key, or Signing Secret have not yet been provided. |
| `AWAITING_VERIFICATION` | Credentials saved; awaiting health check verification. |
| `CONNECTED` | Remote provider verified and operational via `/health` ping. |
| `CONNECTION_ERROR` | Health check failed; remote provider rejected credentials or is offline. |
| `DISABLED` | Integration explicitly disabled by platform administrator. |

## 7. Migration Checklist for External SaaS Teams

When a SaaS team is ready to connect their live API:
1. Implement the `/partner/v1/tenants` and `/partner/v1/tenants/:id/subscriptions` endpoints according to this specification.
2. Provide a Base URL, API Key, and HMAC Signing Secret to Hexalyte Central Platform administrators.
3. Configure webhook emission to `https://resellers.hexalyte.com/api/v1/webhooks/:productId` for subscription events.
4. Admin updates product integration in Admin Panel from `MANUAL` to the product's remote provider key and enters credentials.
5. Admin clicks **Test Connection** (`POST /admin/saas-products/:id/health-check`).
6. Once connected, automated provisioning immediately begins without requiring any code changes to the reseller workflow.
